## This phase actually ran against live Groq, Cohere, and Qdrant

Unlike every prior phase, P3 needed real external LLM/embedding/vector-store calls to prove
anything — there's no way to unit-test "does the model pick the right tool" or "does Qdrant
return the right notes." The credentials in `.env` (flagged as unconfirmed provenance back in
P0) turned out to be **real, working, billable keys** — confirmed by genuine `200 OK` responses
from `api.groq.com`, `api.cohere.com`, and a live Qdrant Cloud cluster. This resolved the open
P0 question, but also means this repo cannot be pushed publicly without rotating those keys
and scrubbing them from git history first — see the end of this doc.

## Bugs found via live testing (none of these were catchable by unit tests alone)

1. **Planner sent `{"SKU": "denim"}` instead of `{"sku": "denim"}`** — the prompt only gave
   tool names + prose descriptions, so the model guessed a reasonable-looking but wrong field
   name. Fixed by including each tool's actual `model_json_schema()` in the planner prompt
   (`src/agents/planner.py`), not just a description. This is the single most important fix in
   this phase — matches how real tool-calling systems work (schema, not prose).
2. **`lookup_buyer_history`'s `buyer_id` field was filled by the planner with `"current
   buyer"`** — a placeholder string, because the LLM has no way to know the real UUID from
   conversation text. Fixed the same way `tools_spec.md` §0.1 already handles `sme_id`: added
   `buyer_id` to `ToolContext` (the orchestrator already resolved it from the inbound message)
   and the orchestrator now overrides whatever the planner supplied for that one field before
   validating — same principle, applied to a field the doc's schema didn't originally flag.
3. **Qdrant `query_points` 400'd**: "Index required but not found for buyer_id." Qdrant
   requires an explicit payload index before filtering on a field — `ensure_collection` now
   creates one (`PayloadSchemaType.KEYWORD`) once per SME collection.
4. **Seed script's idempotency check was too coarse** — `_seed_buyers_and_history` bailed out
   if *any* buyer existed for the SME, so once P2's manual testing had created a few throwaway
   buyers, the P3 seed's actual returning-buyer (Ali Traders, with real order history) never
   got inserted for the rest of this build. Fixed to check per-buyer (by `wa_id`) instead of
   "any buyer at all."
5. **My own JSON log formatter silently dropped exception tracebacks** — `logger.exception()`
   calls only showed the message, not the traceback, which is exactly what I needed to diagnose
   bug #2 above. Found the gap while debugging live, fixed `JsonFormatter` to include
   `formatException()` when `exc_info` is present, added a test.
6. **mypy 1.11.1 (the P0-P1 pin) crashes on numpy's stubs** (`numpy` arrives transitively via
   `qdrant-client`/`cohere`, never imported directly) — a PEP 695 stub-syntax parse error on
   one version, an internal `AssertionError` in the cache-serialization path on another.
   Bumped mypy to 2.3.0 (fixes it cleanly) and pinned `numpy==2.1.3` explicitly so dependency
   resolution can't silently reintroduce the incompatible version.

## Other decisions

- Planner uses `response_format: json_object` (one call returns both `parsed_intent` and
  `tool_calls`), not native OpenAI-style function-calling — see `docs/agent_prompts.md` for
  why (native tool-calling responses typically have empty `content`, leaving nowhere for the
  one-line intent summary the audit drawer needs).
- Tool-execution failures inside the orchestrator loop are caught narrowly
  (`pydantic.ValidationError`, for planner-supplied malformed args) — anything else propagates
  up to `agent_worker`'s top-level `except Exception`, which is the deliberate, documented
  safety boundary (message stays `is_pending=true`, matches "Groq down → retries on next
  message" from `MVP_v1.md`'s own P3 done-means). `lookup_buyer_history`'s Qdrant/Cohere call
  is the one exception with its own narrower try/except, since semantic context is explicitly
  degradable per `tools_spec.md` (aggregate history still returns correctly even if the
  semantic lookup fails).
- The actual reply "delivery" now goes through `resolve_channel(...).send()`
  (`src/channels/widget.py`) instead of a direct DB write in the orchestrator, restoring
  CLAUDE.md §7.5's channel-abstraction discipline that P2 had accidentally bypassed (the
  message row is written by `AuditRepository` in the same transaction as the audit entry;
  widget's `send()` is a documented no-op since delivery *is* that row existing).
- No automatic retry scheduler for failed agent processing — a failure leaves the message
  pending until the same conversation gets a new inbound message (which re-triggers
  processing). Building a real retry queue is more than a hackathon MVP needs.

## What to expect

- Buyer asks "denim kitni hai" → agent replies with the exact seeded numbers (450 pieces,
  Rs. 1200.00/piece), verified against a live Groq call, not just a fake in a test.
- Returning buyer ("purana customer hoon, discount milega?") → agent correctly reports
  `is_returning=true`, 2 past orders, 5% typical discount, and the current stock/price — all
  numbers traced to real seed data and real tool outputs, narrated by a real LLM without
  inventing anything.
- Audit entry captures the exact tool call sequence, real (corrected) inputs, real outputs,
  the real model name, and real latency.
- `docs/agent_prompts.md` documents the literal prompt text used.

## Verification performed

- **Structural**: `mypy --strict` (2.3.0) clean, `ruff` clean, `black --check` clean, 33/33
  pytest passing for real inside Docker (includes `orchestrator_test.py`'s three tests, which
  verify the deterministic-narrator invariant purely at the code level using a fake
  `ChatCompleter` and a fake tool with a known number — no live LLM needed for that guarantee).
- **Live, against real infrastructure** (not simulated): sent real widget messages through the
  full stack and confirmed via direct DB inspection — first-time buyer gets a correct stock
  quote with exact numbers; returning buyer gets correct history + discount + stock, chaining
  two tools correctly; rate limiting and idempotency (carried over from P2) still hold with
  the agent loop attached. All three of Groq, Cohere, and Qdrant were exercised with real,
  successful API calls, not just structurally reviewed code.

## Known gaps

- No automatic retry scheduler (see Other decisions above).
- Cross-tenant isolation for the agent loop specifically (P3's own done-means asks for "create
  a second SME, verify SME1's Excel data isn't queried") was not separately tested this
  session — the underlying `sme_id`-scoped repository pattern is identical to what's already
  relied on everywhere else in the app, but this specific scenario wasn't run live.
- P95 latency budget (<5s per turn) — the one live multi-tool turn observed was ~6s including
  a real Qdrant round-trip; single-tool turns were ~1.1s. Not enough samples to call this
  budget met or missed with confidence.
