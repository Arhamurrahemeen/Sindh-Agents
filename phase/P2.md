## Deviation: pulled `GET /api/agents` forward from P4

`MVP_v1.md`'s own P2 done-means checklist requires "dashboard home reflects the new
conversation within 5s" — but `GET /api/agents` (the route that carries `recentConversations`,
per `api-contract.md` §2.1) is filed under P4's file list. Rather than invent an undocumented
ad hoc endpoint to satisfy P2's checklist, built the real route now, matching the spec exactly.
P4 doesn't need to build it again — just the fuller styled UI (agent cards grid, etc.) against
an already-working route. The current dashboard rendering is deliberately minimal (a plain list
with an unread badge) since the polished version is P4's job.

## Other decisions

- Rate limiting (`rate_limit.py`) is an in-process sliding-window counter, not a literal
  token-bucket — functionally equivalent for a flat "N per minute" limit and much simpler to
  get right. Same single-worker caveat as everything else in-process so far: resets on restart,
  doesn't span workers.
- Idempotency cache (`idempotency.py`) is also in-process with a 24h TTL — same caveat.
- Buyer's name is **not** persisted to `localStorage` (only the random, non-PII `wa_id` UUID
  is) per `CLAUDE.md` §7.4 ("No PII in localStorage... nothing else"). The widget re-prompts
  for a name on every fresh page load; message history isn't restored across reloads either
  (P2 has no "fetch conversation history" endpoint — only inbound POST and outbound long-poll
  from a cursor). Flagging as a known UX gap, not silently working around the invariant.
- `resolve_pilot_sme`/`resolve_pilot_agent_id` hardcode the single-pilot-SME assumption
  `api-contract.md` §3.1 explicitly sanctions for MVP ("single pilot SME per widget instance").
  The real `phone_number_id` → `sme_id` mapping table is Phase 2 (post-MVP), not this P2.

## Bugs found during build

1. **`seeds/pilot_sme.py`**: `VALUES (..., :tool_bindings::jsonb, ...)` — SQLAlchemy's `text()`
   bind-parameter parser and Postgres's `::` cast operator collide when there's no space
   between them; the parameter was left as literal `:tool_bindings::jsonb` in the compiled SQL,
   causing `PostgresSyntaxError`. Fixed with `CAST(:tool_bindings AS jsonb)`, the standard
   workaround.
2. **`lib/backend-fetch.ts`**'s `proxyToBackend` silently dropped the request's query string
   and the `Idempotency-Key` header — fine for `/me` (no params) but broke `/api/widget/outbound`
   (needs `wa_id`/`after`/`wait`) and would have broken the inbound idempotency contract
   entirely. Fixed to forward both.
3. **Docker Desktop's host disk (C:) was at 99% full**, which killed two consecutive
   `docker compose build` runs with no output and made `docker system df`/`docker compose logs`
   hang for minutes. Not a code bug, but blocked all verification until resolved — pruned
   Docker's build cache + dangling images + orphaned volumes (3.5GB reclaimed, all Docker-only,
   nothing project-related touched) after confirming with the user first, since it touches
   shared machine state beyond this project.

## What to expect

- Visit `/widget` → bubble bottom-right → expand → prompted for name → greeting bubble appears.
- Type "denim kitni hai" → send → bubble shows the buyer's own message (no reply yet).
- `POST /api/widget/inbound` (direct or via the Next proxy) returns 200 with a `messageId`.
- Dashboard home (after logging in as the pilot SME) shows each conversation with buyer name,
  message preview, and an unread badge — confirmed with three different test buyers.
- Retrying the same `Idempotency-Key` returns the identical `messageId`, no duplicate row.
- The 31st inbound request from the same `wa_id`+IP within 60s returns `429 RATE_LIMITED`.
- `GET /api/widget/outbound?wa_id=...&wait=N` blocks for `N` seconds then returns
  `{"messages":[],"hasMore":false}` when nothing new has arrived.

## Known gaps

- No message-history restore on widget reload (see Deviations above).
- Widget UI hasn't been visually inspected in an actual browser — only curl/HTML-string
  verification. The "WhatsApp-like, emerald accent" visual sanity check from the done-means
  checklist is unverified in the literal sense of a human looking at it.
- Rate-limit and idempotency state don't survive a backend restart or span multiple workers
  (in-process, documented in both source files).
