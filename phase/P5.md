## The eval harness — how it actually exercises the real stack

`harness.py`'s `run_case()` calls `process_buyer_message` (the real orchestrator — real Groq
planner + narrator, real tool execution against the seeded Postgres) directly, the same
function `orchestrator_test.py` unit-tests with fakes. The one seam it uses is the
already-existing `audit_writer` Protocol parameter: the harness wraps the real
`AuditRepository.write_agent_reply_with_audit` in a spy that captures `tool_calls` before
delegating to the real writer — so the eval both gets to assert on exactly which tools ran
*and* still writes real audit rows, no application code changed to support this.

## Bugs found (via the first real eval run — not hypothetical, these are live findings)

1. **A real, live production bug, not just a corpus mistake**: buyer messages referencing a
   relative date ("kal" — tomorrow) caused `check_delivery_slot` and `record_order_intent` to
   silently never execute. Root cause: the planner is a **single-shot** LLM call — it decides
   *all* tool calls for a turn before any tool has run, so when a buyer says "kal," the
   planner has no way to know what date "kal" resolves to (it hasn't seen `get_current_date`'s
   result yet, because that tool hasn't executed). It left `requested_date`/`delivery_date` as
   `""`, which failed Pydantic validation, which the orchestrator's existing
   "planner gave invalid input, skip gracefully" path (`orchestrator.py`'s
   `except ValidationError`) quietly absorbed — no crash, no error surfaced to the buyer or
   the SME, just a tool that silently never ran. **This is a real gap in the live product**:
   today, a buyer asking "kal delivery ho sakti hai?" gets a reply that doesn't address
   delivery timing at all, with nothing in the logs beyond a `warning`-level line easy to miss.
   Not fixed in this phase — this is an architecture question (does the planner need a
   two-phase design where `get_current_date` runs first and its result feeds a second
   planning pass, or should the orchestrator resolve relative-date words itself before
   handing them to date-typed tool inputs?) bigger than "P5 polish" scope per `MVP_v1.md`'s
   own "Deliberately NOT in P5: new features... anything not in P0–P4 does not enter P5."
   Flagging clearly rather than silently patching around it. The corpus was fixed by using
   explicit dates ("1 August 2026 ko") in delivery/order-confirm cases instead of "kal" —
   this sidesteps the gap for eval purposes without hiding that it exists in the live agent.
2. **Two corpus cases asserted numbers a natural reply had no reason to state** — not a code
   bug, a test-authoring mistake on my part, caught by the very first real run:
   - `buyer-history-returning-ali-traders` asserted `avg_order_quantity` (125) would appear
     verbatim, but a buyer asking "discount milega?" naturally gets a reply about the
     *discount*, not their own historical average order size. Fixed: assert `"5"` (the
     seeded 5% discount) instead — the number the buyer actually asked about.
   - `phrasing-variant-denim-godown`'s buyer message only asked about stock ("kitna stock
     pada hai godown mein?"), not price, but the case asserted the price (`"1200.00"`) would
     appear too. Fixed: dropped the price assertion, kept the stock-count one (`"450"`).
   - Per `docs/eval_spec.md` §4's own stated philosophy, a weak case that's honestly weak is
     better than a strong-looking one that's actually wrong — these two were the latter.
3. **`record_order_intent` still doesn't get called for the two remaining failing cases**,
   even after switching to explicit dates. Re-reading `agent_prompts.md`'s planner prompt:
   "Use only after stock and price are confirmed and the buyer has agreed" — this reads as an
   implicitly multi-turn condition (confirm stock/price in one turn, agree in a later one).
   My test cases compress an entire negotiation into a single message, which the planner may
   reasonably interpret as not yet having its own tool-confirmed stock/price for *this* turn,
   so it doesn't call the tool. This looks like correct, conservative planner behavior given
   its actual instructions, not a bug — left these two cases failing honestly rather than
   rephrasing them into something that no longer resembles a realistic single buyer message.

## `python -m seeds.pilot_sme` now actually runs

`MVP_v1.md`'s P1 and P3 "Run" sections both document `cd apps/backend && python -m
seeds.pilot_sme` as a command, but `seeds/pilot_sme.py` had no `if __name__ == "__main__":`
guard — running it did nothing (no error, silently a no-op, since `run()` is async and was
never invoked at module scope). Needed for the eval's CI job to seed a fresh Postgres service
container before running the corpus, so added the two-line guard
(`asyncio.run(run())`) — additive, no existing behavior changed (the app's own
`DEV_AUTO_SEED` startup path is untouched).

## CI (`.github/workflows/ci.yml`)

Three jobs, matching `CLAUDE.md` §8 + `MVP_v1.md`'s P5 done-means:

1. **`backend-checks`** — mypy --strict, ruff, black --check, pytest. Uses dummy env var
   values (no real DB, no real Groq/Cohere/Qdrant) — current unit tests never touch a real
   service (Protocol-based fakes throughout, per `CLAUDE.md` §8's "mock only external
   services" rule), so nothing here needs to resolve to anything live.
2. **`frontend-checks`** — tsc --noEmit, eslint, prettier --check, vitest, plus a grep-based
   hardcoded-Roman-Urdu-string check mirroring `MVP_v1.md`'s own P5 "Run" section command.
3. **`eval`** — spins up a real Postgres service container, migrates + seeds it, then runs
   `python -m evals.roman_urdu` for real. **Needs `GROQ_API_KEY` (and optionally
   `QDRANT_URL`/`QDRANT_API_KEY`/`COHERE_API_KEY`) added as GitHub repo secrets before this
   job will actually pass** — without them it will legitimately fail (every case "crashes"
   on an invalid Groq client), which is correct, expected behavior for an unconfigured
   secret, not a workflow bug. This is the one thing in this phase I could not verify inside
   CI itself (no push access to configure repo secrets) — verified locally instead by running
   the exact same command inside Docker against the real dev stack (see above).

## Lighthouse — real numbers, not simulated

No GUI browser or Android device is available in this environment, so this is a genuine
best-effort, not the "real device" measurement `dashboard_spec.md` §6 ultimately wants — but
Chrome exists on the host machine, so this ran for real: `npm run build && npm run start`
(actual production build, not dev mode), real headless Chrome via `npx lighthouse`, mobile
form factor, against all 5 spec'd screens (auth cookie obtained through the real OTP flow for
the three authenticated ones).

| Screen | Performance | Accessibility | Best Practices | SEO |
|---|---|---|---|---|
| `/login` | 94 | 100 | 96 | 100 |
| `/` (home) | 94 | 95 | 96 | 100 |
| `/conversations` | **88** | 96 | 96 | 100 |
| `/conversations/[id]` | 91 | 95 | 96 | 100 |
| `/widget` | 96 | 100 | 96 | 100 |

4 of 5 screens clear both the ≥90 performance and ≥95 accessibility bars. **`/conversations`
misses the performance target (88 vs ≥90)** — consistent with its production build's own
First Load JS number:

```
├ ƒ /conversations                       5.1 kB          153 kB   ← over the 150KB budget
├ ƒ /conversations/[id]                  11.9 kB         142 kB
├ ○ /login                               5.67 kB         116 kB
├ ○ /widget                              5.17 kB         116 kB
├ ƒ /                                    175 B          96.1 kB
```

`/conversations` is the only route over `dashboard_spec.md` §6's 150KB/route budget, and the
only one under the 90-performance bar — same root cause. Likely contributor: `FlagMenu`
(a `"use client"` component per row) plus `Badge`/`DropdownMenu` primitives loaded for every
row in the list, where `/conversations/[id]` only pays that cost once (`AuditDrawer`). Not
fixed this phase — flagging with the actual numbers rather than guessing a fix without
measuring it first.

- Lighthouse CLI itself crashes on this Windows host during its own temp-directory cleanup
  (`chrome-launcher`'s `rmSync` on its cache dir hits `EPERM` — a known Windows quirk, likely
  antivirus or an open file handle). Doesn't affect the report: the JSON output is written
  before the crash in every run; only the process's own exit code is nonzero. Worth knowing
  if a future run "fails" — check for the JSON file before assuming the audit itself failed.
