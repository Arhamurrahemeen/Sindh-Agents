## Deliberate deviations from `dashboard_spec.md`

1. **Audit drawer via `?audit=<messageId>` query param, not parallel +
   intercepting routes.** Spec §3.5 literally describes
   `@audit/[messageId]/page.tsx` parallel-route interception. That pattern is
   real complexity for a hackathon timeline with limited payoff — the
   query-param approach still gives a shareable URL and ≤1-tap access (the
   spec's actual requirements), just via `searchParams` read in the existing
   `conversations/[id]/page.tsx` server component instead of a second route
   tree. If this becomes a real product, the parallel-route version is a
   contained follow-up, not a rewrite.
2. **No `data-table` (TanStack) for desktop conversation list.** Spec §3.3
   asks for a `DataTable` on desktop, cards on mobile. Shipped: the same
   card/row layout at all viewports. Adding TanStack Table is a new
   dependency for a table that, at pilot scale (≤1000 convos/SME per
   `db_schema.md` §5), doesn't need virtualization or column sorting yet.
3. **Search is a native GET `<form>`, not a debounced client-side input.**
   Typing + Enter submits the form and Next re-renders the (still fully
   server-component) list page with `?q=`. Zero client JS for search. Spec's
   "debounced `onChange`" implies live-as-you-type filtering; this trades
   that for zero bundle cost, which matters more against the ≤150KB/route
   budget in §6 than incremental search UX at pilot scale.

Both list and detail screens stayed server components for this reason — no
`useEffect`-based fetching, no client-side data cache, matching §1's "Server
Components + `fetch` with `revalidate: 0`" default.

## Bugs found (all via live testing against the real stack, not just types)

1. **`auditMessageId` was wired to the wrong ID.** Initial
   `message_repository.list_for_conversation` selected `messages.audit_entry_id`
   (which stores the `audit_entries.id` primary key) and returned that as
   `auditMessageId`. But `GET /api/audit/[messageId]` looks up by
   `audit_entries.message_id` — the *agent reply's own message ID* — per
   `api-contract.md` §2.4 ("same as `auditMessageId` on the conversation
   detail"). Every audit-drawer open would have 404'd. Caught by an actual
   end-to-end smoke test (real widget message → real agent reply → fetched
   the conversation detail → the returned `auditMessageId` genuinely 404'd
   against `/api/audit/[id]`), not by types (both are plain `string`, so
   nothing structural would have caught this). Fixed by dropping the
   unneeded `audit_entry_id` column read entirely and using the message's own
   `id` when `sender == 'agent'` — simpler than the original code, not just
   corrected.
2. **`Badge` (shadcn-generated) crashes when rendered directly from a Server
   Component.** `components/ui/badge.tsx` imports `Slot` from `radix-ui` for
   its `asChild` prop; that import chain calls `React.createContext` at
   module scope, which Next's RSC compiler forbids unless the module is
   marked `"use client"`. Every prior use of `Button`/`Badge` in this repo
   happened to be inside an already-`"use client"` component (login page,
   `SindhAgentsWidget`, `Sheet`), so this was latent until P4's
   `conversations/page.tsx` and `conversations/[id]/page.tsx` — both server
   components — rendered `<Badge>` directly. 500'd with "createContext only
   works in Client Components." Fixed by adding `"use client"` to
   `badge.tsx` (a pure presentational leaf — no functional loss; Server
   Components can render Client Component children freely, just not the
   reverse). `button.tsx` has the identical pattern but isn't yet used
   directly from a Server Component, so left alone — fix it the same way if
   that changes.
3. **Bad `cursor` on `GET /api/conversations` was silently ignored instead of
   `400`-ing.** `_decode_cursor` returned `None` on any decode failure, and
   the caller treated `None` as "no cursor supplied" (first page), which
   contradicts `api-contract.md` §2.2's explicit `400 BAD_REQUEST` error for
   this case. Fixed by having `list_paginated` raise `ValueError` when a
   *non-empty* cursor fails to decode, caught in the route handler and turned
   into the documented 400. Found by deliberately testing the error path
   (`?cursor=not-a-real-cursor`), not by the happy-path smoke test.
4. **`mask_phone` had no defined behavior for `phone IS NULL`.** Widget
   buyers (`BuyerRepository.get_or_create`) only ever get a `wa_id` session
   UUID — `phone` is genuinely `NULL` for every non-seeded conversation. The
   original `mask_phone(phone: str)` (written in P0/P1 for the SME owner's
   phone, which is never null) would `IndexError` on `phone[3]` for any
   widget buyer. `GET /api/conversations` and `/api/conversations/[id]`
   both call it on buyer phone, so this would have 500'd on literally every
   conversation created through the widget (i.e., almost all of them).
   Fixed by widening the signature to `str | None` and returning `"—"` for
   the missing case.
5. **Next.js dev server inside Docker doesn't reliably hot-reload on host
   file edits.** The `web` service's bind mount (`../apps/web:/app`) makes
   edits visible inside the container immediately (confirmed via `docker
   compose exec web cat ...`), but webpack's dev-mode file watcher kept
   serving a stale compiled module graph after the `badge.tsx` fix above —
   confirmed the fix was on disk inside the container, yet the same
   `createContext` crash persisted until the container was restarted, and
   even then persisted until the anonymous `.next` cache volume
   (`infra_web_next`) was cleared. `docker-compose.dev.yml`'s own claim
   ("edits reload without a rebuild") holds for simple component edits in
   practice elsewhere in this session, but not for this specific
   module-graph-level change — worth knowing if a future fix "isn't taking
   effect" during dashboard work: try a `web` container restart before
   assuming the code is wrong.

## Other decisions

- `mask_phone` moved from `api/auth.py` into `services/phone.py` so
  `api/conversations.py` doesn't duplicate it — the only cross-file reuse
  this phase needed, no bigger refactor attempted.
- Backend repositories return raw (unmasked) `buyer_phone`; masking happens
  in the API layer (`conversations.py`), matching the existing pattern in
  `auth.py`'s `/me` route — repositories stay presentation-agnostic per
  CLAUDE.md §6.
- `FlagMenu` (three-dot menu, per `dashboard_spec.md` §3.3's "MVP: three-dot
  menu" note) calls the already-built `POST /api/conversations/[id]/flag`
  and the audit drawer's flag button calls the *same* endpoint — the spec
  itself says both surfaces share one flag action (§2.5), so no
  message-level flagging was built separately.
- `ToolCallRow` uses a native `<details>/<summary>` instead of an
  accordion component — not in the approved shadcn list (§1), and the
  native element gives collapse/expand for free with zero JS.

## What to expect

- `/` shows an agent card per agent (status dot, messages-today count,
  "View conversations →"), then the existing recent-conversations list,
  now under a proper heading.
- `/conversations` — tabs (Sab/Naye/Nishaan lagaye hue), a search box that
  filters by buyer name or phone digits, one row per conversation with a
  flagged badge, unread dot, and a three-dot flag/unflag menu.
- `/conversations/[id]` — WhatsApp-style thread, buyer messages left/white,
  agent messages right/emerald, each agent bubble has a magnifier that opens
  `?audit=<id>` on the same URL.
- Audit drawer shows the buyer's original message, the agent's one-line
  parsed intent, each tool call (collapsed, tap to expand — real inputs/
  outputs, e.g. `read_excel_stock` returning `stock: 450` verbatim), the
  agent's reply, total latency, model name, and a flag button.

## Verification performed

- **Structural**: `mypy --strict` clean on every P4 file, `ruff` clean,
  `black --check` clean (backend); `tsc --noEmit` clean, `eslint` clean (only
  pre-existing shadcn-generated import-order warnings in `sheet.tsx`,
  untouched by this phase), `prettier --check` clean, `vitest` 5/5 passing
  (frontend). `pytest` 34/34 passing inside Docker.
- **Live, against the real stack** (not simulated): sent a real widget
  message through the full agent loop to generate a genuine conversation +
  audit entry, then exercised every new endpoint against it —
  `GET /api/conversations` (list, tab filter, search-by-digits), `GET
  /api/conversations/[id]` (detail + mark-read side effect confirmed),
  `POST /api/conversations/[id]/flag` (on/off), `GET /api/audit/[messageId]`
  (real tool call trace, verbatim numbers) — plus every documented error
  path: `401` (no session), `404` (nonexistent conversation, audit lookup on
  a buyer message), `400` (bad `tab`, bad `cursor`). Then booted the actual
  Next.js dev server in Docker and fetched the real SSR HTML for `/`,
  `/conversations`, and `/conversations/[id]?audit=...` with a real session
  cookie obtained through the real OTP flow, confirming rendered content
  (agent cards, conversation rows, message bubbles, audit drawer contents)
  matched what the backend returned — this is how bugs #1, #2, and #4 above
  were actually caught, not through types or unit tests.
- No browser GUI is available in this environment, so nothing was
  click-tested (the flag three-dot menu's client-side mutation, the audit
  drawer's open/close interaction) — those were verified structurally
  (typecheck + the same `apiFetch` pattern already proven working in
  `dashboard-header.tsx`'s logout button) and via their underlying HTTP
  routes directly, not by clicking in a real browser.

## Known gaps

- Conversation list has no desktop `data-table` (see deviations above) —
  same layout at all viewports.
- No Lighthouse/bundle-size measurement yet for the two new routes — that's
  explicitly P5 scope (`MVP_v1.md`).
- Client-side interactions (flag toggle menu, audit drawer open/close) were
  not click-tested in an actual browser — see verification notes above.
- `button.tsx` has the same latent Server-Component/`Slot` crash risk as
  `badge.tsx` had; not hit yet because every current usage is already behind
  a `"use client"` boundary, but the same fix applies if a future page
  renders `<Button>` directly from a server component.
